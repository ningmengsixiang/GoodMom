**最需要先看的五件事**

1. **仓库里没有 V2.5–V2.7。** Git HEAD 停在 V2.4（2026-09-07），工作树是 V2.7（2026-09-11）：**122 个未跟踪文件 + 78 个已修改文件未提交**，含整个 `goodmom-vue/` 包、站点构建管线、`site/fragments/`、`.claude/` skill、`.storybook/`、4 个 React 组件与 `package-lock.json`。而**所有守门工具都只在工作树上跑**，所以本地"全绿"、仓库对外是空的（P0-1 / P0-2 / P0-3）。
2. **唯一首页的主导航与 CTA 点击后跳到 404。** `site/index.html` 有 **90 个**被写成 `href="href="#gm-mod-…"` 的畸形锚点（生成器 `build-site.py:943` 重复输出了一段 `href="`）。已起静态服务实测：目标 `/site/href=` 返回 **404**（P0-4）。

4. **CI 中有两步永远不可能通过**：`site-parity.mjs` 的输入 `site/.baseline/` 被 `.gitignore` 主动排除（P0-6）；`vue-pkg-build` 与 `open-pkg-typecheck` 依赖未入库的 `goodmom-vue/`（P0-2）。
5. **团队唯一的渲染级对比度工具本身是坏的**：`a11y-dom.py` 丢弃 `alpha`，把半透明背景当实色算，读数**夸大 2–3 倍**（已用报告值精确复现证明），且跑不完、不入 CI、无阈值（P1-20）。**在修好它之前，`docs/a11y-dom-report.md` 的数值不能作为修复依据。**

### P0-3 · 所有门禁都跑在"工作树"上，没有任何检查校验交付物是否已入库

**证据**：`scripts/` 下 15 个工具（audit / a11y / a11y-dom / coverage / check-status-map / build-site / gen-* / redirect-legacy / site-* / patterns-smoke）**全部**以当前目录文件系统为输入；`ci.yml` 依赖 `actions/checkout` 的检出结果，但**没有任何步骤比对"磁盘内容 == Git 内容"**。

后果非常具体：

- `python3 scripts/audit.py` 在工作树上报「✅ 通过」，而它所校验的 `scripts/build-site.py`、`site/fragments/`、`goodmom-vue/`、`.claude/` 在仓库中并不存在。

**建议**：新增无需网络的 job：

```yaml
- name: 交付物必须已入库
  run: |
    if [ -n "$(git status --porcelain --untracked-files=all)" ]; then
      echo "存在未提交/未跟踪文件，交付不完整："; git status --short | head -40; exit 1
    fi
```

### P0-4 · 唯一首页的 90 个锚点被写成 `href="href=…"`，点击主导航/CTA 后 404

**证据**

```
$ grep -o 'href="href=' site/index.html | wc -l
90
$ git show HEAD:site/index.html | grep -o 'href="href=' | wc -l
0
```

首个样本（`site/index.html:292`）：

```html
<a class="btn pri" href="href="#gm-mod-preview-index" data-mod="preview-index"">视觉规范</a>
```

**根因（一行）** —— `scripts/build-site.py:943`：

```python
return f'{pre}href="{target}" data-mod="{mod}"{post}'
```

`pre` 是 `re.sub(r'(<a\b[^>]*?\shref=")([^"]+)(")', one, html)`（`:945`）的第 1 组，**本身已经以 `href="` 结尾**，于是被输出了两次。

**为什么用户一定会踩到**：浏览器把该属性值解析为字面量 `href=`，默认导航仍然会执行 —— 因为全局委派处理器（`site/index.html:6886-6897`）匹配 `a[data-mod]` 后**从不调用 `preventDefault()`**：

```js
document.addEventListener('click', function(e){
  var a = e.target.closest('a[data-mod], a[href^="#gm-mod-"]');
  if(!a) return;
  var id = a.getAttribute('data-mod') || a.getAttribute('href').replace('#gm-mod-','');
  if(activate(id, false)){ /* 只切模块，不阻止默认跳转 */ }
});
```

**已实测**（静态服务）：

```
GET /site/index.html -> 200
GET /site/href=      -> 404   ← 点击导航后跳到这里
```

**影响面（按 `data-mod` 统计）**：`site-spec` 44 · `preview-examples` 18 · `site-manual` 10 · `preview-index` 6 · `preview-mobile` 5 · `preview-patterns` 3 · `site-index` 3 · `site-docs` 1。覆盖**首屏 hero CTA（视觉规范 / 组件与状态 / 阅读文档）、顶部主导航、章节索引（`:6749-6780`）、手册与文档目录（`:2334-2365`）**。

**范围（已逐页核实）**：该缺陷**只存在于 `site/index.html`**（51 行含畸形串，共 90 处）。打印版 `preview/manual.html` 与 7 个重定向桩（`site/docs.html`、`site/spec.html`、`site/manual.html`、`preview/{index,examples,mobile,patterns}.html`）均为 **0** 处 —— 修复面是局部的、可控的。

**同一缺陷也已写进源片段**（`site/fragments/` 合计 16 处：`preview-index` 13、`preview-examples` 2、`preview-patterns` 1），所以**只改生成器不够，片段本身也要修**。

**为什么门禁没拦住**（三重失明）：

- `scripts/build-site.py --check` 只证明"产物 == 片段"，而片段里也有同样的畸形串 → **OK**；
- `scripts/site-parity.mjs`（15/15）比对的是"模块 vs 原页面"的类名/id 差集，不校验属性值合法性 → **通过**；
- `scripts/site-smoke.mjs`（41/41）用 JS 点击 `a[data-mod]`，模块确实切换了，但**没有断言默认导航被阻止、也没有断言 href 合法** → **通过**。

**建议**

1. `build-site.py:943` 去掉多余的 `href="`：`return f'{pre}{target}" data-mod="{mod}"{post}'`。
2. **同时修片段**（或从干净基线重新抽取），然后重建 `site/index.html`。
3. 加断言：`assert 'href="href=' not in html` 与 `assert re.search(r'href="#gm-mod-', html)`。
4. `site-smoke.mjs` 增加"导航后仍停留在本页（未发生文档级跳转）"断言。
5. 给全局委派加 `e.preventDefault()`（这是"模块内路由"的常规做法），作为纵深防御。

### P0-5 · 应用侧镜像包导出 5 个组件，但缺失它们全部 CSS，镜像守卫按设计看不见

**证据**

`frontend-app/packages/gm-arco-ui/src/index.ts` 导出了 `GmEmpty`、`GmSpin`、`GmSkeleton`、`GmTag`、`GmSteps`，该包 `package.json` 声明的样式产物**只有** `src/gm.css`（201 行）。

机械比对 `theme.css` 与 `gm.css` 的选择器集合：

```
theme.css 选择器: 132 | gm.css 选择器: 92
theme.css 中缺失于 gm.css 的 gm-* 选择器: 37
  .gm-btn / .gm-btn:not(.arco-btn-disabled):hover / .gm-btn.arco-btn-primary / .gm-btn-hc.arco-btn-primary …
  .gm-empty / .gm-empty .t / .gm-empty .d / .gm-empty .gm-empty-ic
  .gm-spin / .gm-spin i            .gm-skeleton / .gm-skeleton i
  .gm-tag / .gm-tag i / .gm-tag.lg / .gm-tag:focus-visible
  .gm-steps / .gm-step / .gm-step::before / .gm-step .gs-dot / .gm-step.finish/.process/.error …
  .gm-status-dot                   .gm-risk-it:focus-visible
gm.css 独有选择器: 0（即 gm.css ⊂ theme.css）
```

**实际后果（不只是"少样式"）**：镜像 `GmStatusTag.tsx:28` 渲染 `<span className="gm-status-dot" style={{background:c}} aria-hidden="true"/>`，而 `gm.css` 中 `gm-status-dot` 出现 **0** 次 —— 而 `theme.css:93` 正是给这个色点 `width:7px;height:7px` 的地方。也就是说**应用侧的状态标签色点是一个 0×0 的不可见空 span**，"颜色 + 文字双通道"退化成单通道。`docs/审查决策记录.md:83` 还声称这个缺陷"已补齐"。

**同一个缺口的另一面（Token 层）**：`gm.css` 的浅色 `:root` 块（`:51-68`）**完全没有** 6 个 `--lg-sem-*`、5 个 `--mmh-solid-*`、5 个 `--mmh-m5-*` —— 它们只出现在暗色段。也就是说应用侧**浅色主题下的主题覆盖机制是静默失效的**：任何按规范写 `color: var(--lg-sem-positive)` 的样式都不会生效（Vue 的 `components.css:49-54` 正是这么写的，且没有兜底）。目前应用侧组件用 TS 取色而非 `var()`，所以尚未暴露 —— 属于"一旦按规范写就坏"的定时问题。

**为什么门禁看不见**：`scripts/audit.py:334-335` —— `if rel == "theme.css": continue`，`mirror_sync()` 从设计上就跳过这一对样式表（注释称"应用侧对应 gm.css，为有意不同的封装样式"）。**"封装差异"能解释包装器样式不同，但解释不了"导出的组件完全没有样式"。**

**建议**

1. 把共享的组件样式抽到第三个文件（如 `components.css`），由 `theme.css` 与 `gm.css` 同时引用；或让 `gm.css` 成为 `theme.css` 的超集。
2. 把 `mirror_sync()` 升级为**选择器集合比对**：`gm.css` 缺少任何 `theme.css` 中的 `.gm-*` 选择器即 FAIL。
3. 对"导出即必须有样式"加断言（`index.ts` 导出的组件名 → 其根类名必须能在样式源中找到）。

### P0-6 · `site-parity.mjs` 依赖一个被 `.gitignore` 排除的目录，CI 中永远无法通过

**证据**

- `scripts/site-parity.mjs:24` 需要 `site/.baseline/` 下的 8 个基线页面（`site-index` / `preview-index` / `preview-examples` / `preview-mobile` / `preview-patterns` / `site-spec` / `site-manual` / `site-docs`），用于比对"模块 vs 原页面"的类名/id/主题变量差集。
- 但 `.gitignore:38` 明确忽略该目录：`site/.baseline/`，且 `git ls-files site/.baseline | wc -l` = **0**。
- `ci.yml` 的 `site-build` job 却要跑 `node scripts/site-parity.mjs`（`ci.yml:86`）。

```
干净检出（仅 161 个已入库文件）中：
  site/.baseline/ 不存在 → 8 个模块的比对全部失败
```

**为什么这是独立于 P0-2 的阻断项**

即使把 5 个未入库脚本（P0-2）和 `site/fragments/`（P0-1）全部提交，`site-parity` 这一步仍然必红 —— 因为它的输入被 `.gitignore` 主动排除。这是一个**自相矛盾的交付设计**：一个被 CI 依赖的必需输入，同时被声明为"非交付内容"。

**附带说明**：`.gitignore:38` 的注释称基线快照"仅供热节保真度校验，非交付内容"。这在"本地校验"语境下成立，但一旦它成为 CI job 的输入，"非交付内容"与"CI 必需"就不能并存。二者必须选一。

**建议**（任选其一，需明确记录）

1. **把基线纳入交付**：从 `.gitignore` 移除 `site/.baseline/`，把 8 个基线页面提交入库（它们是 8 个片段的历史副本，体积可控），并在 `site/README.md` 说明其用途与更新时机。
2. **让 site-parity 自带基线**：把基线改存到 `site/fragments/` 同级或 `scripts/baseline/` 下的交付目录；或改为"若无基线则从 `git HEAD` 的对应文件取"（`build-site.py` 已有"抽取源与产物同路径时从 git HEAD 取原版"的先例可复用）。
3. 无论哪种，CI 中都应显式断言基线存在，避免"缺文件即静默跳过"。

## 2. P1 · 严重

### P1-1 · `GmStatusTag` 在 React / Vue 中渲染方式完全不同，且两者在浅色下均不满足 WCAG AA

**两条实现路径（同一组件名，视觉不可互换）**

- **React**（`goodmom-ui/src/components/GmStatusTag.tsx:25-31`）：`<Tag color={c}>`。Arco 对自定义色的处理是 `node_modules/@arco-design/web-react/es/Tag/index.js:119` → `colorStyle.backgroundColor = color`，并加类 `.arco-tag-custom-color`，其样式为 `color: var(--color-white)`。→ **白字压在语义色实底上**。
- **Vue**（`goodmom-vue/src/components/GmStatusTag.vue:82-88`）：`style = { color: resolved, background: tint(resolved, 0.13), borderColor: tint(resolved, 0.32) }`。→ **13% 淡化底 + 语义色文字 + 32% 描边**。

已核实设计系统**没有**任何 `.arco-tag` 覆写（`grep -rn "arco-tag" goodmom-ui/src/theme.css frontend-app/packages/gm-arco-ui/src/gm.css goodmom-vue/src/styles/*.css` 无命中），故上述 Arco 行为直接生效。

**实测对比度**（12px 小字，AA 阈值 4.5:1；大字豁免不适用）

| --- | --- | --- | --- |
| positive | `#2F8F76` | 3.95:1 ❌ | 3.39:1 ❌ |
| info | `#4A76D0` | 4.38:1 ❌ | 3.73:1 ❌ |
| attention | `#B9771C` | 3.67:1 ❌ | 3.17:1 ❌ |
| risk | `#D35466` | 4.02:1 ❌ | 3.42:1 ❌ |

**为什么是问题**

### P1-12 · React 与 Vue 的组件 API 与默认行为大面积分歧

**证据（机械比对声明的 props 与默认值）**

| 组件 | React 有、Vue 无 | Vue 有、React 无 |
| --- | --- | --- |

4. **React 重演了 Vue 已修掉的 ResizeObserver 报错**：`GmResponsiveView.vue:83-95` 明确注释"在回调里同步改样式 → 触发新一轮尺寸变化 → Chrome 抛 ResizeObserver loop completed with undelivered notifications"并用 rAF 规避；`GmResponsiveView.tsx:70-84` 仍在回调里**同步** `setWidth(...)`。
5. **Token 引用能力不对等**：Vue 有 `SEMANTIC_VAR`/`FIVE_VAR`/`SEMANTIC_LABEL`/`SEMANTIC_CSS_SUFFIX`（`tokens/status.ts:20,40,49,59`）与 `design.ts:18 gradActionHc`，React 全无 —— 于是 React `GmRiskPicker.tsx:13` 只能硬编码变量名 `"var(--mmh-m5-"+k+",…)"`。而 `goodmom-vue/src/tokens/design.ts:2` 却声称"字段与 React 版完全一致"——**不实**。
6. **文档化的 Cascader 修复没进库**：CHANGELOG 与决策记录称外部点击误判已用 `composedPath()` 快照修好，但该快照**只存在于 `site/index.html:4617-4620`**；两个库仍是 `root.contains(ev.target)`（`GmCascader.tsx:348`、`GmCascader.vue:341`）。
7. **类名规范只有 Vue 遵守**：`14-命名与术语规范.md:23` 的规范形态是 `.gm-btn--primary`，Vue 的 `components.css` 出现 32 次，`theme.css` 出现 **0** 次（React 侧输出的是 `.arco-btn-primary`）。
8. **同一 `GmTag`/`GmSteps` 在不同包的不同目录**：React 在 `src/adapters/`，Vue 在 `src/components/`。

**建议**：建立"双库契约表"并在 CI 断言 props/默认值/ARIA 一致；优先修默认外观、`closable` 事件、`GmProgress` 四项属性、`GmResponsiveView` 的 rAF 规避。

### P1-20 · 唯一的渲染级对比度工具本身是坏的：丢弃 alpha 导致读数夸大 2–3 倍，且无法跑完、不入 CI、无阈值

这是本次审计**最重要的方法论发现**：仓库里唯一的渲染级可访问性证据，其工具本身存在确定性缺陷。

**缺陷 1 · `alpha` 被丢弃，半透明背景被当作不透明实色（工具核心公式错）**

`scripts/a11y-dom.py:20-24`：

```js
function rgb(t){var m=t.match(/rgba?\(([^)]+)\)/);if(!m)return null;
  var p=m[1].split(/[, ]+/).map(Number);return [p[0],p[1],p[2]];}
```

正则同时匹配 `rgb()` 与 `rgba()`，但**只返回前 3 个分量 —— alpha 被丢掉**。于是 `:30` 的透明度判断失效：

```js
if(col&&col!=='transparent'&&col!=='rgba(0, 0, 0, 0)'){var a=rgb(col);if(a&&a[3]!==0){stack.push(a);break;}}
```

`a[3]` 恒为 `undefined`，`undefined!==0` 恒为**真** → 任何带 alpha 的背景都会被推入前景栈并**当作实色**参与对比度计算。

**实证（用报告值反推，精确吻合）** —— 源 `site/fragments/preview-examples.html:43-45`：

| class | 声明 | 工具口径（把 alpha 当实色） | 复算 | 报告值 | 吻合 |
| --- | --- | --- | --- | --- | --- |
| `.r` | `color:#D35466; background:rgba(239,106,123,.13)` | `#D35466` vs 实心 `#EF6A7B` | **1.30** | **1.34** | ✅ |
| `.o` | `color:#B9771C; background:rgba(242,178,92,.18)` | `#B9771C` vs 实心 `#F2B25C` | **1.98** | **1.98** | ✅ |

→ 报告里 `span 检查异常 1.34` / `span 待复查 1.98` 这类数值是**方法论伪影**，真实承载面是 13%/18% 淡色片叠在近白玻璃上，而不是实心 `#EF6A7B`。**若照报告数值去"修"，会修错方向。**

**修正后的真实结论（以最乐观的近白承载面 `#FFFFFF` 重算，即上界）**

| 前景 | 对比度 | 12px 文字需 4.5:1 | 判定 |
| --- | --- | --- | --- |
| `#2F8F76` | **3.95:1** | ❌ | 确认失败 |
| `#4A76D0` | **4.38:1** | ❌ | 确认失败（临界） |
| `#B9771C` | **3.67:1** | ❌ | 确认失败 |
| `#D35466` | **3.89:1** | ❌ | 确认失败 |
| `#757E8E` | **4.09:1** | ❌ | 确认失败 |
| `#7A5CE0` | **4.74:1** | ✅ | 通过 |

即：**`preview-examples` 的六色语义片 6 项中 5 项不达 AA** —— 这仍然是**确认真失败**，只是真实幅度比报告小约 3 倍。这与 P1-1（React 白字压实底 5/6 不达标）是**同一组色值的两种呈现方式**，互相印证：**问题在语义色板本身偏浅，而不是某一种渲染方式。**

**缺陷 2 · 工具跑不完，且残留会自我污染（与 P2-2 是同一根因的两面）**

- `a11y-dom.py:14` 在**导入时**就构造 `PAGES = glob("site/*.html") + glob("preview/*.html")`；`:63` 又把探针写到 `dirname(page)/_a11y_probe.html` —— **探针落在自己的输入 glob 里**。
- 因此任何被中断遗留的探针都会在下次运行时**被当成待测页面**，而更早页面的 `finally`（`:86`）会先把它删掉，导致读取失败：

```
FileNotFoundError: [Errno 2] No such file or directory: 'site/_a11y_probe.html'   (a11y-dom.py:64)
```

→ **报告永远写不出来。** 实测该脚本在本环境 600s 超时被杀且未产出报告；直接验证无头 Chrome（`--headless=new --dump-dom`）对最简页面 120s 内也无任何输出。

**缺陷 3 · SIGTERM 后孤儿进程继续跑并重建垃圾文件**

脚本没有信号处理，主进程被 `SIGTERM` 后 python 子进程仍存活，继续遍历页面并**重新生成** `_a11y_probe.html`。这解释了为什么探针文件会"删掉又出现"（与 P2-2 记录的实时复现一致）。

**缺陷 4 · 不是门禁：不入 CI、无阈值、无时间戳**

- `grep -rn "a11y-dom" .github/workflows/ci.yml` → **0 处引用**（仅 `scripts/audit.py:200` 把它列进"允许存在于 docs 的文件名单"）。
- `scripts/a11y-dom.py:110-114` 仅在**探针未执行**时 `sys.exit(1)`；**失败计数 `failN` 只写进 markdown 表，永不退出非零** → 报告里 843 项失败**不阻断任何流程**。
- 报告**无生成时间戳、无工具版本、无阈值声明**，读者无法察觉它已过期（见 P2-4）。

**缺陷 5 · 反向盲区：迁入 `site/index.html` 的失败从未被重测**

报告对 `site/index.html` 只记 **4** 项失败，但 `preview/examples.html`（71 项）+ `preview/index.html`（147 项）的内容在 V2.7 合并**迁入**了 `site/index.html`。也就是说**当前唯一对外的首页的真实失败数被报成 4**。

**量化（按报告 8 行原始数据）**

| 项 | 数值 |
| --- | --- |

**建议**

1. **先修工具再谈数字**：`rgb()` 必须返回 alpha 并做**背景合成**（沿祖先链逐层 `over` 合成），否则所有半透明片/玻璃面读数系统性错误。

4. 在修好工具前，**`docs/a11y-dom-report.md` 的具体数值不应作为修复依据**，只可用作"待复查清单"。

### P1-21 · `redirect-legacy.py` 把"文件不存在"判定为"不是重定向"

**证据**（`scripts/redirect-legacy.py:125`）

```python
cur = io.open(path, encoding="utf-8").read() if os.path.exists(path) else ""
```

文件缺失时 `cur` 为空串，随后的重定向断言必然失败：

```
干净检出（preview/patterns.html 未入库）：
FAIL 以下旧页面还不是重定向：['preview/patterns.html']
EXIT=1
```

**为什么是逻辑缺陷**：**"缺失" ≠ "内容错误"**。这个校验的本意是"旧入口必须已被改写为重定向"，但实现把两种完全不同的状态（文件不在 vs 文件在但不是重定向）合并成同一个失败。在干净检出的 CI 里，它报出的错误信息（"还不是重定向"）与真实原因（文件根本不存在）不符，会把维护者引向错误的修复方向。

**建议**：缺失与内容错误分开报告 —— 缺失应报"未入库/文件不存在"，内容不符才报"不是重定向"；两者都失败但信息必须可区分。

### P2-2 · 探针与截图写进交付目录且未被忽略，残留即污染门禁

**证据**

- `scripts/a11y-dom.py:62-65` 把探针页写到被测页面**同目录**（`site/_a11y_probe.html`、`preview/_a11y_probe.html`），正常由 `finally`（`:85-90`）删除。
- `scripts/site-smoke.mjs:303` 写 `site/.smoke-index.png`（**该脚本从不清理**，实测 469,680 B）。
- 三者**都不在 `.gitignore` 中**（`git check-ignore` 均无命中）。`.gitignore:24` 只覆盖了 `fuyouaicansai/_probe_*.html`，**漏了 `site/` 与 `preview/`**。

**实际发生的后果（本次审计期间实时复现）**：运行仓库自己的 `a11y-dom.py` 后，残留的 `site/_a11y_probe.html`（内容是被测页面的完整副本，实测含 **598 处小写 hex**）直接让 `audit.py` 变成红色：

```
[FAIL] hex-case：1 个文件含小写 hex：[('site/_a11y_probe.html', ['#1E6B52(小写)', …])]
```

即：**跑一次仓库自己的无障碍工具，就能让仓库自己的强制门禁失败**；若进程被中断（CI 超时 / Ctrl-C），该文件会长期留存。此外 `a11y-dom.py:13` 的 `PAGES` 用 `glob("site/*.html") + glob("preview/*.html")`，下次运行会把**探针页本身当成被测页面**。

**两个加剧该问题的额外机制（实测确认）**

1. **探针落在自己的输入 glob 里 → 工具自我污染并崩溃**：`a11y-dom.py:14` 在导入时就构造 `PAGES = glob("site/*.html") + glob("preview/*.html")`，而 `:63` 把探针写到 `dirname(page)/_a11y_probe.html`。因此**任何遗留探针都会在下次运行时被当成待测页面**；更早页面的 `finally`（`:86`）又会先把它删掉，于是读取失败、**报告永远写不出来**（详见 P1-20）。
2. **`SIGTERM` 后孤儿进程继续跑并重建文件**：脚本无信号处理。主进程被杀（如 600s 超时）后 python 子进程仍存活，继续遍历页面并**重新生成**探针 —— 这解释了"删掉又出现"的现象，也意味着"手动删一次"并不能真正清理。

**建议**：探针改写系统临时目录（`tempfile`）；`PAGES` 排除 `_*`；加信号处理与整体超时兜底；`site-smoke.mjs` 的截图同样写到临时目录或运行后删除；把 `site/_a11y_probe.html`、`preview/_a11y_probe.html`、`site/.smoke-index.png` 加入 `.gitignore` 兜底。

### P2-3 · 焦点可见性：宽选择器压制 + 组件级缺口 + 门禁文件级假通过

**压制规则**（`goodmom-ui/src/theme.css:94`）

```css
.gm-tag,.gm-steps,.gm-status-dot,[class*="gm-"]:focus{outline:none}
```

`[class*="gm-"]:focus` 会命中**任何**类名含 `gm-` 的元素——近乎全部 GoodMom 组件。而恢复焦点环的 `:focus-visible` 规则在 React 主题中只有 **7 条**（`.gm-tag`、`.gm-steps .gs-dot`、`.gm-risk-it`、`.gm-link`、级联 3 处、`.gm-vlist__viewport`）。

**两库缺口对比**

| 选择器 | React `theme.css` | Vue `components.css` |
| --- | --- | --- |
| `.gm-btn:focus-visible` | **无** | 有（`:23`） |
| `.gm-status-tag__close:focus-visible` | **无** | 有（`:88`） |

即：在 React 侧，按钮与状态标签关闭按钮既被宽规则压制、又没有 `:focus-visible` 恢复（Vue 侧两者都有），键盘用户可能完全看不到焦点。

**门禁为何放过它**：`a11y.py:20` 的判断是**文件级** —— 只要同一文件里出现任意一处 `:focus-visible` 即通过。`theme.css` 有 7 条，于是报 **OK「outline:none 均伴 :focus-visible 兜底」**（已按该逻辑复算确认）。

### P2-16 · CI 的站点 job 依赖"上一步泄漏出来的后台服务"，且冒烟在真机上没有独立起服务

**证据**

`scripts/site-smoke.mjs` 的文件头自己写明需要静态服务，且默认 URL 硬编码：

```js
/**
 * 用法：node scripts/site-smoke.mjs   （需先在仓库根起一个静态服务，见下）
 *   python3 -m http.server 5288      # 仓库根
 */
const URL = process.env.SITE_URL || "http://localhost:5288/site/index.html";
await page.goto(URL, { waitUntil: "networkidle" });
```

而 `.github/workflows/ci.yml` 的 `site-build` job 是这样接的：

```yaml
- name: 合并保真度（各模块 vs 原页面：类名/id/主题变量）
  run: |
    npm install
    python3 -m http.server 5288 --bind 127.0.0.1 &
    sleep 2
    node scripts/site-parity.mjs
- name: 单一首页冒烟（41 项：模块切换/样式隔离/交互/键盘/重定向）
  run: node scripts/site-smoke.mjs        # ← 本步骤没有起服务
```

**已复现的失败模式**（这是本项的决定性证据）：

```
$ SITE_URL=http://127.0.0.1:59999 node scripts/site-smoke.mjs
page.goto: net::ERR_CONNECTION_REFUSED at http://127.0.0.1:59999/site/index.html
    at scripts/site-smoke.mjs:29:12
EXIT=1
```

**服务起着时，脚本本身完全正常**：`EXIT 0` / `41 PASS / 0 FAIL` / `41/41 通过`。所以**脚本没坏，是 CI 接线坏了**。

**问题**

1. **隐式依赖跨步骤的后台进程**：服务在"合并保真度"步骤里用 `&` 启动，冒烟在**下一个步骤**里才用。GitHub Actions 每个 `run:` 是独立 shell，且会清理步骤派生的后台进程 —— 一旦不存活，冒烟步骤就以 `ERR_CONNECTION_REFUSED` 失败，报错信息与真实原因（站点回归）毫无关系。
2. **没有就绪门控**：只有 `sleep 2`，没有轮询到 HTTP 200。
3. **`--bind 127.0.0.1` 与 `localhost` 的族不匹配**：URL 用 `localhost` 而服务只绑 IPv4。Node 20 默认开启 `autoSelectFamily` 会回落 IPv4，因此**这一项通常无害**（此前担心的 IPv6 问题不成立）—— 真正致命的是第 1 点。
4. `SITE_URL` 虽可覆盖，但 CI 没有设置它，等于把"服务在哪"交给环境默认值。

**为什么值得修**：这两点是"站点回归门禁本身可能假红/假绿"的来源 —— 与本文档第 6 节的主题一致：门禁的可靠性没有被当作交付物对待。

**建议**：把服务启动、跑两个脚本、关服务放进**同一个** `run:` 块，用 `nohup … &` + 轮询直到 HTTP 200 再跑；显式设置 `SITE_URL=http://127.0.0.1:5288/site/index.html`；补 `npx playwright install --with-deps chromium`；并在脚本内加入"服务不可达"的显式错误提示（区分"环境问题"与"站点回归"）。

**同一 job 内的其它连线缺陷（均为干净检出下必失败，已逐个复现）**

| 步骤 | 干净检出下的实际结果 |
| --- | --- |
| `python3 scripts/build-site.py --check`（`ci.yml:78`） | `can't open file '…/scripts/build-site.py'`，**EXIT 2**（脚本未入库） |
| `python3 scripts/redirect-legacy.py --check`（`:80`） | 同上 **EXIT 2**；即使脚本入库，也会因 `preview/patterns.html` 未入库而 **EXIT 1**（见 P1-21） |
| `node scripts/site-parity.mjs`（`:86`） | `MODULE_NOT_FOUND`；脚本入库后仍因 `site/.baseline/` 被 gitignore 而失败（见 P0-6） |
| `python3 scripts/check-status-map.py --ci`（`:40`） | **EXIT 2**（脚本未入库） |
| `npm run build:vue`（`:99`） | `npm error No workspaces found: --workspace=@goodmom/vue` |
| `python3 scripts/build-site.py --check`（脚本已入库、`site/fragments/` 未入库） | `ERROR 未找到 site/fragments/，先执行：python3 scripts/build-site.py --extract`，**EXIT 1** |

> 注：`vue-pkg-build` 自己的四条产物断言与 Token grep 是**正确的**（本地实测 `dist/index.js` 40625 B、`index.cjs` 38289 B、`style.css` 22033 B、`index.d.ts` 29891 B，且 `--mmh-grad-action-hc` 确在 `style.css` 中）——失败纯粹因为包没入库。
