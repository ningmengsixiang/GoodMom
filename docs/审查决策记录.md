## D8 · 主按钮与品牌主色统一（D5 遗留结案，2026-09）

## D9 · 主行动改为品牌粉 + 深字（D8 取值上移，2026-09）
- **背景**：D8 把主行动定为品牌同族加深档 `#C44C74→#B23A63` + 白字（4.53–5.71 过 AA），但设计负责人要求按钮**直接用品牌主色 `#F77FA3`**。
- **约束（算术）**：白字在 `#F77FA3` 上仅 **2.46:1**，连大字号 3:1 都不到 → 「按钮 = 主题色 + 白字」这条路**不存在**。要让按钮用上 `#F77FA3`，只能把文字**由白转深**。
- **裁决**：`--mmh-grad-action-hc` = `linear-gradient(135deg,#FFC4D6 0%,#F77FA3 100%)`（= Rose-300→Rose-500，**品牌粉上半段**）+ 文字 `#343A46`。取值理由：不得含 `#E85D8F` 深端——该色上深字 3.48、白字 3.28，**两个方向都不达标**，故只取品牌粉上半段。
- **实测**（CSS 规范插值 `t=(x+y)/(W+H)`，按 03·3.2.2 尺寸表算**文字框内最坏点**）：XS 5.16 / S 5.14 / M 5.10 / M 长文案 4.89 / L 5.00 —— 全尺寸 ≥4.5；渐变亮端 7.67、暗端角落 4.63。**余量比 D8 的 4.53–5.71 更大**。
- **落地**：token（`theme.css` 真源 + `gm.css` + 9 处页面声明与 fallback）；以该 token 为底的控件文字由白转深（71 处自动替换）；**Arco primary 默认白字必须显式覆盖** —— `theme.css` `.gm-btn.arco-btn-primary`、`gm.css` 同名规则、`theme.css` `.gm-btn-hc` 三处补 `color:#343A46!important`；`fuyouaicansai/goodmom-redesign.html` 主变量 `--g` 及其 **7 处白字控件**、手册顶栏 `.top a`（`gen-manual.py` + `site/manual.html` 同步）。

  `[data-theme="dark"] .glass{…}`（原语义：`<html data-theme>` 是**祖先**）改写成
  `.gm-mod--x [data-theme="dark"] .glass`（**后代**）—— 而 `rewrite_page_dark_css` / `rewrite_page_dark_js`
  已把该属性改挂在**模块根自身**上，模块内部根本没有带该属性的后代，于是**全部暗色规则永不命中**。
- **裁决与落地**：在 `scope_selector` 增加一条——以 `[data-theme=…]` / `:where([data-theme=…])` 开头
  的选择器必须写成**复合**（`.gm-mod--x[data-theme="dark"] …`），而不是后代。复合形式特异性更高，
  也顺带解决了"暗色底纹 vs 模块底色同特异性、靠声明顺序决定胜负"的隐患。
- **验证**：点击真实开关后模块底色 `rgb(27,26,33)`（= 02 · 2.1.9 的 `#1B1A21`）、文字 `#F3EFEC`；`page-qa.mjs` 增加
  「挂上 `data-theme` 后 400 个采样元素的颜色/底纹是否变化」的指纹判定，避免把"未实现暗色的模块"误报成"暗色对比度失败"。

### 工具口径校正（避免把合规实现报成违规）

渲染级检查必须自己先"站得住"，否则会诱导错误的修复方向：

- **禁用态豁免**：WCAG 1.4.3 明文豁免失效/禁用控件；禁用态用低对比表达"不可用"是正确做法，不该被算成违规。
- **规范正文 ≠ 界面**：`site-spec` / `site-manual` 是规范正文阅读器，正文里的 🟢 图例与版本沿革是**文档内容**，不计入「界面禁 emoji」与「同页版本号不一致」。
- **`:after` 热区是合规实现**：10 章明确允许用 `::after` 扩热区，伪元素没有 `getBoundingClientRect`，只量元素盒会把它误判成违规。
- **`02 · 2.4` 只管「组件与容器」**：任一短边 <32px 的微元素与 `display:inline` 的行内盒子（`code` 芯片、进度条、色点）不在圆角档位管辖内 —— 把 18px 套到 12px 高的 chip 上反而是错的。
- **暗色能力缺口 ≠ 违规**：`dark-missing` 记为 P3。token 层是否支持暗色由 `audit.py` 的 `dark` 检查守；各展示模块是否自带暗色皮肤是**能力缺口**，登记不阻塞。

## D16 · 按钮视觉统一（主按钮"描边错行发脏" + 白底按钮"描边廉价"，2026-09）

- **用户反馈**：① 主按钮的描边与分层有错行、看起来脏；② 白底按钮的描边很廉价。
- **实测诊断（先量后改，不靠目测）**：把 5 个页面的全部按钮变体渲染后 dump 计算样式，结论两条 ——
  1. **不透明实底套了玻璃边光**。02 · 2.5 的「1px 白色描边（55–65%）+ 顶部白内高光」是给**半透明玻璃面**的
     受光边缘；主按钮经 D9 改为**不透明**品牌粉渐变后没摘掉它们 → 白边在浅粉上「亮端看不见、暗端看得见」，
     一圈边缘深浅不均（＝描边错行），再叠 inset 白高光成双线发糊（＝脏）。阴影又混了中性蓝紫灰（02 · 2.6 本要求色相统一）。
  2. **浅底控件的边用了白色**（`rgba(255,255,255,.7~.85)`）。玻璃面板的白边靠**底下彩色光斑**才成立；
     实心白按钮底下没有光斑 → 白边等于没有边，轮廓糊掉（＝廉价）。`--lg-shadow-sm` 又偏弱，没有浮起感。
  3. **同一按钮在各页各写一套**：实测主按钮阴影有 `0 10px 24px` / `0 6px 16px` / `0 8px 18px` 三种；
     更有 `preview-index` 的一组 `!important` **只覆写 background/color，把旧设计的 border 与 inset 高光全留下**——
     这是"同一个主按钮看起来错行"的直接根因。另发现 `preview-mobile .cta` 在**同一条规则里**把 `border` 与
     `box-shadow` 各声明两次（后者静默胜出），把新配方吃掉。
- **裁决 · 三条统一配方（写入 03 · 3.2.4.1，站点与两个组件库同源）**：
  - **A 主按钮**：不透明品牌粉底 → `border:none`，边缘清晰度交由**同族玫色双层阴影**
    `0 1px 2px rgba(178,58,99,.22), 0 8px 20px rgba(240,127,163,.30)`。
  - **B 白底按钮**：边改 **02 · 2.7.1 同源的暖中性 hairline** `var(--lg-divider)`（暗色档自动翻白）+
    02 · 2.6 双层柔影；玻璃感由半透明白 + `blur(16px)` 保留。
  - **C 描边按钮**：`1.5px solid rgba(232,93,143,.45)`（带 alpha 的玫瑰，替代纯色饱和硬边）+ 极淡玫影。
- **同档统一（同一缺陷类）**：浅底交互控件 `chip` / 级联选择器 `cas-t`·`cas-btn` / 搜索框 / 勾选框 `chk` /
  开关轨道 `sw` 的边一律改 `--lg-divider`。**不动**：`.glass`/`.card`/`.panel` 等半透明玻璃面的白边
  （那是 02 · 2.5 的材质定义，底下有光斑才成立）。

### D17 补记 · 两个真实踩到的工具盲区（已各自加门禁）

本轮在改样式时**自己制造并自己发现**两个"静默失效"缺陷，二者都不会报错、只能靠机械检查：

1. **未闭合的 `/*`**：往 Vue `components.css` 的 `.gm-spin` 前插注释时漏写 `*/`，

   —— 浏览器不报错、页面不报错、既有 8 个门禁全绿，**Vue 侧的加载指示器直接没有样式**。
   它是被 `check-style-parity.py` 以"单边选择器"的形式**间接**暴露的（解析器把吞掉的规则算作不存在），
   排查耗时明显。→ 新增 `audit.py css-syntax`：两库样式表 + 站点片段样式段的注释/花括号必须平衡。负向测试已验证。
2. **多余的一个 `}`**：用正则替换骨架块时留下，导致解析器错位（同样表现为假的"单边选择器"）。
   同一门禁一并覆盖。

**教训（写进纪律）**：用正则改大段 CSS 时，**改完必须跑机械平衡检查**；
"浏览器没报错"不等于"样式生效了" —— 注释与花括号是两类会静默吞规则的语法错误。
这两道门禁的价值不在于发现得多，而在于它们拦住的都是**没有任何其他信号**的故障。

## D19 · 档案数据呈现（Descriptions · 折叠 · 玻璃表格，2026-09）

- **背景**：用户要求「档案数据呈现（Descriptions · 折叠 · 玻璃表格），进一步优化」。

### 实测证据

### 本轮做法：一份配方 + 渲染级守门

1. **外壳新增「数据呈现层」**（`scripts/build-site.py`）：`.gm-tbl` / `.gm-desc` / `.gm-fold`，
   全站唯一配方；页面侧只加 class，**19 处私有实现全部删除**（含 6 处死规则、1 处 JS 里的残留选择器）。
   独立演示页（不并入首页）保留同源一份，由门禁**逐项比对两份的数值**，任一侧漂移即 FAIL。
2. **操作列基线正式定义**：TB-15-01 引用「17.2 基线 `.ops`」，但 17.2 里**根本没有这个小节**
   （悬空引用，站点也因此分裂出 `.op`/`.ops` 两个名字）。已在 17 · 17.2.3 补上，并统一为 `.ops`。
3. **行高 44–52 变成可算的算术**：`padding 12×2 + 行高 20 + 分隔 1 = 45`；
   单元格内联元素一律 ≤26（表格内头像 26、徽章 26、`mini` 按钮 26）→ 最坏 `12+26+12+1 = 51`。
   配套两条硬规则：单元格**不折行**（折行 → 65px），单元格**直接子元素** `flex-wrap:nowrap`
   （页面里的 `.block span{flex-wrap:wrap}` 会把头像与文字拆行 → 实测行高 80px）。
4. **横滑容器取代 `display:block`**：旧实现给 `<table>` 自己加 `display:block;overflow-x:auto`，
   而这会在 Chrome / Firefox 里**把表格语义从无障碍树里抹掉**（TB-15-02 要求保留表头语义）。
   改为外层 `.gm-tbl-wrap{overflow-x:auto}`，并给每个 `<th>` 补 `scope="col"`。
5. **折叠按 11.2.6 重做**：拦截 `summary` 点击 → `grid-template-rows: 0fr ⇄ 1fr` 过渡 300ms、
   箭头 220ms 旋转、标题行 44 热区、同组一屏 ≤3 组、补 `aria-expanded`/`aria-controls`
   （原生 `<details>` 不报这两个属性，读屏不知道这是可展开控件）。

### 顺带修掉的四个"只有渲染才看得见"的缺陷

1. **特异性陷阱（本轮最阴的一条）**：模块内规则经构建会被加上 `.gm-mod--x ` 前缀 → 特异性 (0,2,0)，
   与外壳的 `.gm-tbl .badge`（0,2,0）**同权**，而模块样式在文档里更靠后 —— **外壳那条静默失效**。
   实测：`.gm-tbl .badge{padding-top:3px}` 完全没生效（算出来仍是 `4px 12px`），行高停在 53。
   修法：凡覆盖"模块里已有的类"，一律写成 `.gm-tbl td .badge` 这类 ≥ (0,2,1) 的形式。
   同一根因还咬了两次：`.gm-tbl td>*`（0,1,1）被 `.block span`（0,2,1）压回去。
2. **折叠代理层的 padding**：`0fr` 轨道的基尺寸取子项 min-content，而 padding 不可压缩 ——
   代理层自带 14px 下内边距时，收起后残留 14px 高。内边距必须放到再下一层内容元素上。
3. **Token 命名空间断裂**：数据呈现层读系统命名（`--lg-text-secondary` / `--lg-divider`），
   而 `preview-patterns` 只有私有命名（`--t2` / `--line`）→ 暗色档"页面翻了、表格没翻"，
   实测暗底深字 **1.61:1 / 1.50:1**。修法是**惰性别名**（`--lg-text-secondary:var(--t2)`），
   一处定义、暗色自动跟随。
   ⚠️ 但别名**只能接配方真正读的 Token**：我一开始顺手把 `--lg-text-tertiary` 也接了，
   结果页面里 `var(--lg-text-tertiary, 深色兜底)` 的写法从"走兜底"变成"走别名值"，
   禁用态链接从可读的兜底色变成 `#8A92A3`（**3.12:1**），被 `a11y-dom` 判为新增确证失败。
   门禁已加白名单：别名多接未使用的 Token 即 FAIL。
4. **改名后的静默失联**：`.op` → `.ops` 时漏改了 `@media(max-width:767px)` 里的热区选择器
   `.op a::after` → ≤767px 的操作链接热区只剩 **13×36**（page-qa 一次抓出 17 条 P1）。

### 防回归：静态 + 渲染两级

- **`audit.py data-present`**（静态）：外壳配方数值逐项校验（14px/600/次级色/hairline/
  12px 内边距/不折行/内联不折行/横滑容器/tabular-nums）、折叠 300ms+220ms+44 热区、
  折叠代理层不得带 padding、描述列表 caption+body-sm+单行省略、**站点片段零私有实现**、
  每个 `<th>` 必须 `scope`、用了配方就必须接系统 Token 且别名白名单、
  独立演示页配方与外壳**逐项相等**。

  （并报出撑破行的内联元素）、操作列右对齐、`tabular-nums`、`display:table`（禁止用
  `display:block` 换横滑）、描述列表 value 的 body-sm 与单行省略、折叠的 44 热区 / 过渡 /

## D21–D27 · 产品前端工程的七项决定（19 章）

> 背景：设计系统（01–18）已经定型，产品前端工程此前只有一份"组件演示"骨架

> **落点＝本仓 `frontend-app`**；**技术方向＝React + Arco + `@goodmom/ui`**。

### D21 视觉风格：基调不变，按端分密度
沿用液态玻璃基调（01/12），**不重新定义风格**；四类界面（家长端 / 医护工作台 / 机构运营 /

Token 与状态词就会分叉，暗色档与无障碍要各修一遍。

### D22 技术方案：React 18 + TS + Vite + Arco + `@goodmom/ui`
锁定 react 18.3.1 / typescript 5.9.3 / vite 5.4.21 / @arco-design/web-react 2.66.16 / dayjs 1.11.23。
**离线可构建**是硬约束（依赖已固定、无外网），因此路由、请求、全局状态三件套走最小自研，
每件都做成"可替换的一层薄壳"，升级路径写在 19.2.5（换 react-router / react-query / zustand
只改 `shared/` 一个文件，业务零改动）。
**未采纳**：引 Tailwind / CSS-in-JS（会与 `gm.css` 的优先级关系纠缠，收益不抵风险）。

### D23 UI 组件库：三层选型（Arco 原生 → Gm 封装 → 领域组件）
页面选型顺序固定为 ③→②→①；`Gm*` 是**视觉与无障碍的唯一实现处**（19.3）。
页面禁止改 `Gm*` 视觉、禁止自建第二套按钮/标签/空态；Arco 原生组件只作复杂交互件基座，
唯一逃生口是封装层导出的 `ArcoButton`。
配套修掉两处契约缺陷（否则"选型"落不了地）：
`GmProgress` 的像素直径错塞进 Arco 的枚举型 `size`（`diameter` 因此形同不存在，且两处 typecheck 全红）、

## D28 · 虚拟长列表的窗口算法归外壳（window.gmVirtualList）

**背景**：10.11.2 / 11.2.16 的窗口化能力原先只存在于「交互范式」模块的私有 JS 里。
本轮移动端要按 11.2.16 的组合顺序（PullRefresh → Sticky → VirtualList → SwipeAction → LoadMore）
接同一套能力，面临"抄第二份窗口算法"还是"提成外壳唯一实现"的选择。

**裁决**：提成外壳 `window.gmVirtualList(el, cfg)`，两个模块以配置取用
（行类名 / 行高 / overscan / `render(i)` / `onRange` / `onEndReached` 由调用方给，DOM 由它统一产出）。
理由与 `window.gmGrowth`（D20）同源：**抄第二遍的那天，就是两份算法开始漂移的那天**；
而且窗口化最容易出错的正是边界（overscan、inner 高度、距底触发），这类逻辑必须只有一份。

**代价与收益**：交互范式模块的 DOM 与可观测行为逐字保持（类名/aria/inner 高度 66768px/窗口位移），
其冒烟断言未改一行即通过；移动端因此直接拿到 `role=list` + `aria-posinset/setsize` +
PageUp/PageDown/Home/End 的键盘能力。

**踩到的坑（已写进代码注释）**：外壳脚本在文档里位于模块脚本**之后** ——
模块调用外壳渲染器必须等 `DOMContentLoaded`（与 13.2 生长曲线同一个坑，本轮二次踩到）；
另外第一版把渲染器误插进了外壳的 **CSS 注释块**（锚点匹配到 CSS 里的同名注释），
JS 落进 `<style>` 后永不执行，表现为 `window.gmVirtualList is not a function`。

### 一、白条的真因（不是"背景色写错"，是画布没人画）

| 位置 | 真因 | 修法 |
| --- | --- | --- |
| 6 个独立产品页 | 没重置 UA 默认 `body{margin:8px}`（应用被内缩 8px），且 `html` 无背景 → 四周 + 底部一圈**默认白画布**；再叠 `.gm-app{min-height:100vh}` → 文档恒比视口高 16px，底部固定一条白缝（1440 实测 docH=1007 / body 991 / 视口 900） | `html` 画同套玻璃底（根元素背景会传播到画布，连过度滚动区一起覆盖）+ `body{margin:0}` |
| 打印版手册 `preview/manual.html` | 只有局部容器画了底色：粘性页头 `.topm{margin:10px auto}` 的上边距露出白画布 | 同上，补齐根元素底色 |
| `frontend-app/index.html` | 底色在 `src/styles/base.css`，要等 JS bundle 才生效 → 加载前 `<div id="root">` 是空的、全屏无绘制（白闪） | 内联一份根元素底色 |

**判据**：从 `elementFromPoint` 命中的元素往上走到 `<html>`，若**没有任何一层**带非透明底色或渐变，
该点就是"没人画"的白画布 —— 这就是门禁里 P0 的"背景白条"。

### 二、响应式：三处页面级溢出的根因

1. **写死的内联网格**：视觉规范模块里 `<div style="display:grid;grid-template-columns:230px 1fr;gap:18px">` ——
   230px 是硬值，320 档面板内容区只有 264px（230+18+88=336）→ 顶出 45px。改成类名 + 可收缩网格。
2. **`repeat(N,1fr)` 不会收缩**：裸 `fr` 轨道的最小值是 `auto`（= min-content），
   手机模拟里 4 列 KPI 与评分行因此把视口顶出 29px。本仓此前已在别处用 `minmax(0,…)` 修过同类问题，
   这次把**全部 76 处**裸 `fr` 轨道统一改写为 `minmax(0,Nfr)`。
   踩坑：第一版改写用逗号连接轨道（`minmax(0,1.6fr),minmax(0,1fr)`）—— CSS 非法，
   浏览器回退成单列内容宽（768 档实测 861px，反而新增 113px 溢出）。轨道之间必须是空格。
3. **拓扑节点固定 64px**：768 档 `.g2` 仍是两列（列宽 ~340），5 个节点 + 26px 间距 = 424px → 顶出 15px。
   改为 `clamp(44px,6.6vw,64px)`（1440/1024 仍是原尺寸）。

### 三、模块组件：八类"格式错位"的根因与修法

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 快捷工具按钮文字顶出 5~12px | 按钮 `nowrap` + 左右 20px 内边距，固定两列时内容盒只有 72~79px，装不下 84px 的「建立妇女档案」 | 按内容落列 `repeat(auto-fit,minmax(150px,1fr))` |
| 关键指标值顶出 7px | 「128（风险分级 46 · 随访 52 · 报告 30）」整串在一个行内盒里，Chromium 在 Inter+CJK 回退下**找不到断行点**（`overflow-wrap:anywhere` / `word-break:break-all` 均无效） | 拆成「主值 + 括号补充」两个行内盒（顺带把补充降为次级色） |
| 边框演示卡文字溢出（盒只有 40px） | 窄档只写了 `min-width:0`，三张卡被压成 40px 宽 | `flex:1 1 132px`，装不下换行 |
| 规范正文标题溢出 4~8px | **混排标题不会换行**：粗体「总表（Flat Component Registry）」在 250px 内容宽下 254px；CJK 禁则下「（」不得落行末、其后又不许断行，Chromium 不回退到 ASCII 空格处；`line-break:anywhere` 亦无效。插 U+200B **更糟**（被禁则抑制，仍不换行）；**实测唯独 `<wbr>` 有效**（27px→54px，溢出 4px→0） | 生成期在标题/段落/列表的**文本节点**内插 `<wbr>`（按标签切分跳过标签段） |

| 视觉规范模块说明长句（最长 70 字） | "文字居多、乱" | 收敛为短标签（70→34 / 50→42 / 46→28 字） |

| <12px 文字 | 10/10.5/11/11.5px 不在 02 · 2.3 字阶（12/14/15/16/18/24/32）内 | 真实内容一律归到 12px；**设备模拟内**（`.phone/.scr/.pm-screen/.stage/.mkbar` 等按比例缩放画的机身）保留小字号 |

### 四、新增门禁 `scripts/layout-gate.mjs`（70 次扫描 / 7 档）

9 个站点模块 + 6 个独立页 × 4 视图 + 打印版手册 × 断点 320/375/414/768/1024/1440/1920，自起静态服务。分级：

- **P0**：页面级横向溢出；背景白条（未绘制点）
- **P1**：元素出框（未被任何裁切/滚动祖先挡住）；块级兄弟大面积重叠
- **P2**：文字真的被切（`Range` 文本宽 > 内容盒 **且** `scrollWidth > clientWidth`，>4px）
- **P3**（登记不阻塞）：触控热区 <44×44、字号 <12px

**判据里的四个"反假报"设计（都踩过）**：
① 多行 inline 元素的 bounding box 天然互相交叠（文档正文里的 `<code>`/`<b>`）→ 重叠只比**逐行** client rect；
② 44×44 热区扩展伪元素会把 `scrollWidth` 顶大（`.del`/`.sd`/`.stpm` 全被误报"文字被切"）→ 文本溢出必须同时满足两个条件；
③ 粗体全角「）」的墨迹会让 `Range` 宽出 4px 而布局并不溢出 → 同上；
④ 被 `overflow:hidden` / 环境光斑挡住的装饰层（`.gm-pm__amb`）不算出框。

**CI**：新增独立步骤（与逐页质检同 job），`node scripts/layout-gate.mjs`；`docs/layout-gate-report.md` 与另两份报告一样带时间戳、加入工作树清洁检查的排除名单。

## D32 · 页面响应式收口（表格可用性 · 窄屏可达性 · 布局塌陷判据，2026）

- **用户反馈**：「页面要做到响应式」（此前已做过"不溢出"，但**不溢出 ≠ 手机上可用**）。
- **体检口径升级**：从"有没有横向溢出"扩展到"**真实可用性**" —— 表格要不要横向拖、窄屏能不能进到每一个页面、
  内容有没有被挤成一条。逐条实测后修掉三处，并新增一条门禁判据。

### 一、表格：窄屏从"横向拖 400~500px"到"零横滚"

- **实测数据（改动前）**：模块页表格 375 档宽 **748px**、卡片内容宽仅 ~290px —— 每看一行都要横向拖动，
  操作列默认在屏幕外；1024 档也还要滚 178px；站内模块 1440 档滚 **576~641px**。
- **两次失败的尝试（都记在 CSS 注释里，避免再来一次）**：
  1. `overflow-wrap:anywhere` 允许折行 → 行高涨到 **611px**（5 行表 3000px 高），且 320 档仍滚 83px；
  2. "隐藏中间列 + 摘要塞进首列" → 首列被状态/操作两列挤到 ~118px，摘要折成 6 行，**同样 611px 高**。
- **最终方案（17 · 17.1.3）**：每个数据行同时给出两套单元 ——
  桌面用原列（`.gm-tbl__desk`），**≤900 用 `<colspan>` 合并单元**（`.gm-tbl__mob`）承载"对象+状态 / 列名+值 / 操作"三段式；
  窄屏隐藏 `<thead>`（行内自带列名标签，自描述），两套 `display` 互斥（任一视口只有一套进渲染树，AT 不会读两遍），
  **表格语义完整保留**（否掉 `display:block` 的"表格转卡片"，那会丢掉 `<table>` 语义、a11y 门禁也不接受）。
  单一实现 `tbl_row()`，模块侧与独立页四处表格共用。
- **行内动作同步**：一行里有两份状态标签（桌面格 / 合并单元），推进时**两份都改** —— 只改第一份的话，
  窄屏点"记录结果"后可见的那份纹丝不动（用户看不到反馈）。实测窄屏/桌面点击均已生效。

### 二、桌面：宽表不再需要横向拖动

- 表头/单元格 `white-space:nowrap` 是设计系统既有裁决（`page-qa` 的 P2 规则要求表格行高 **44–52px**，
  单元格折行会顶破这一档），所以**不能靠折行缩短表格**；改从"承载它的卡片宽度"入手：
  - 主表卡片在 **≤1200 提前整宽**（原来是 ≤767）；大桌面两列布局给主表列 **`minmax(780px, …)` 最小宽度保障**；
  - **6 列宽表**（含五色分级列）的工作台按数据选布局：`--stack` 在 ≤1600 单列（p03 需 843px，两列只给 690px）。
- **结果**：320–1920 全档、6 个产品 × 全部视图（含 37 个模块页）**零横向滚动**。

### 三、窄屏可达性：≤1280 侧栏隐藏后，业务模块页在手机上完全进不去

- **实测**：切顶栏模式后侧栏 `display:none`，顶栏只有 4 个对象视图页签 —— **37 个业务模块页在窄屏不可达**。
- **修法**：顶栏新增「业务菜单」下拉（仅 ≤1280 显示，内容与侧栏**同一份数据源**：4 个对象视图 + N 个模块页），
  点选即切页并自动收起，支持点外部 / Esc 关闭。
- **踩到的层叠坑**：卡片（`.gm-pm-card`）是定位元素且 `z-index:auto`，与顶栏同层时按 DOM 顺序**盖在展开的面板上**
  （实测窄屏点击被 KPI 卡拦截）；且 `.gm-top{position:static}` 在 ≤1024 断点里，同特异性下**后写者胜** ——
  层叠修正必须写在 `APP_CSS` 最末，否则等于没写。
- **顺带两条**：下拉按钮高度 36px 被 page-qa 的 P1「移动端热区不足」抓到（它是窄屏唯一模块入口，必须 ≥44）→ 改成 44px；
  另外把两个仍在 11px 的遗留文字（`.badge .t`、`.bxrow` 内继承到 11px 的 span）归到 12px 下限。

### 四、门禁

- `layout-gate.mjs` 新增 **P1「布局塌陷」判据**：表格容器被压到 `< min(220, 30% 视口)` 即失败。
  触发原因是一个真实 bug：把工作台菜单拆成两个 `<nav>` 后 `.gm-pm-wb` 多出一个网格项，
  内容被塞进 **212px** 的菜单列、表格横向滚 **641px** —— 而"无溢出 / 无重叠 / 无白条"这些判据**全都看不出来**。
- `products-smoke.mjs` / `product-apps-smoke.mjs` 各新增两条：**桌面表格单行 44–52 且不横向滚动**、
  **窄屏表格零横滚（合并单元 + 行内列名标签 + 表头隐藏）**；独立页再加 **窄屏顶栏「业务菜单」可进模块页**。

## D33 · 双库统一化（零能力差异 · 门禁归一化替代白名单，2026）

### 一、命题与结论

**命题**：`@goodmom/ui`（React）与 `@goodmom/vue`（Vue 3）是同一套设计系统的两个宿主实现，
同名组件**不得有任何能力/默认值/类名/DOM/无障碍差异**。

**结论**：**已达成**。宿主语言层面的**写法**差异（`children`↔默认插槽、具名 prop↔具名插槽、
`value`+`onChange`↔`v-model`）不是"差异"，而是同一能力的两种惯用表达；它们被归一化到同一规范名后
**仍然严格比对**，因此"叫法不同"被承认、"新漂移"照旧失败。

| 不变量 | 门禁 | 结果 |
| --- | --- | --- |
| props / 事件 / 默认值 / 契约类名 | `check-component-contract.py --ci` | 19/19 一致 |
| 共享选择器 CSS 写法（逐字节） | `check-style-parity.py --ci` | 233 个选择器、0 处不同 |
| 暗色覆盖集合 | 同上 | 两侧同名同值 |
| Token 层（浅色 + 暗色两张表） | 同上 | 0 处不同 |
| DOM 与无障碍（渲染级） | 两库 `playground/smoke.mjs` | 60/60 · 39/39 |

### 二、为什么删掉 `KNOWN_DIVERGENCE` 白名单

旧白名单的粒度是「**允许这个组件的 props 不一致**」—— 于是整组 props 与默认值的比对被**跳过**。
代价是实测漏掉了这些真缺陷：

- `GmStatusTag`：`size` 默认值两侧不同（`small` / `default`）→ 同一行代码两个库渲染不同尺寸；
  `size="large"` 在 React 输出一个 CSS 里**不存在**的类名 `lg` → 该 prop 完全无效；
  React 不会从文案推导语义（照 Vue 的写法写就是**灰标签**）；`closeLabel` 只有 Vue 有。
- `GmCard`：`hoverable` / `bodyless` / footer **只有 Vue 有**（能力缺口）。
- `GmEmpty`：`title` 默认值不同（Vue 渲染「暂无数据」，React 什么都不渲染）。
- `GmClientCard`：`actions`（React）↔ `ops`（Vue）同能力异名。
- `GmProgress`：React 基于 Arco 渲染、Vue 自绘 → 两库**进度条 DOM 与类名完全不同**。
- `GmResult`：React 渲染了 `class="gm-result …"`，而 React 侧 CSS **完全没有** `.gm-result` 容器与
  `.gm-result__ic` 规则 → 结果页在 React 下是**无样式裸排**（站点用的是另一份拷贝，所以站点门禁看不见）。

**裁决**：白名单删除，改为「**归一化宿主惯用写法 → 严格集合比对 → 能力对等校验**」。
`IDIOM` 表是唯一允许"叫法不同"的地方，且每条映射都必须通过 `capability_parity()`
（映射里写了哪一侧，那一侧就必须真有那个成员）。

### 三、CSS 与 Token 层：为什么"解析值一致"不够

旧 `check-style-parity.py` 只比**解析后的值**，于是 `var(--lg-border-1)` 与 `1px`、
`var(--lg-divider-hairline)` 与 `var(--lg-divider)` 在浅色档解析值相同 → **门禁绿灯，暗色档分叉**。
实证：`.gm-step.finish .gs-dot` 一侧写 `var(--lg-text-on-inverse)`、一侧写死 `#FFF`，
浅色档都是白、暗色档一个白一个深墨，而门禁全程绿灯。

**裁决**：新增三条严格不变量（B 层）——
① 共享选择器声明**逐字节一致**；② 暗色覆盖集合一致；③ React `theme.css` 与 Vue `base.css` 的
`:root`/暗色段 **Token 表同名同值**（Token 层落在不同文件属文件归属差异，值必须一致）。
三条都做了注入式负向验证（改回 `#000000`、删一条暗色覆盖、把 `var()` 换成字面量，均被精确报出）。

### 四、本轮修掉的真实缺陷（都有实测）

## D34 · 品牌深玫「文字档」加深至 AA（承接 D33 遗留，2026）

### 一、结论

`--mmh-rose-700` 与 `--lg-link` 由 **`#B23A63` → `#A9315B`**（浅色档）。暗色档不变

### 二、为什么必须改

D33 把这条登记为「待裁决」，理由是 `#B23A63` 当初按「**白字压其上** 5.71:1」选定（D7），
没复测它作为**落在暖底上的文字色**。按前端设计规范 **20 · 20.3.2 的硬线**（正文/交互文字 ≥4.5:1，
规范自己已写明「次级色 4.46:1 不能当正文」），实测结果是：

| 承载面 | 改前 `#B23A63` | 改后 `#A9315B` |
| --- | --- | --- |
| `--lg-page-bg`（暖象牙页面底，最暗承载面） | **4.13:1 ✗** | **4.64:1 ✅** |

| 暗色档 `#FF9AB6` on `#1B1A21` | 8.67:1 ✅ | 不变 |

即：**两处最常用承载面（页面底、玻璃卡）都不达标**，受影响的是
`.gm-btn--outline` / `--dashed` / `--text` 的标签、以及所有链接。
「只在某种摆放下才不达标」这种条件式缺陷正是本轮一直在消除的那一类，故不留条件、直接改色。

### 三、取值方法与依据

沿用 **D9 的单点改动方法**：在品牌自有色阶的同族连线上取点。
`#F77FA3`（rose-500，品牌主色）→ `#B23A63`（rose-700，旧深端）这条 RGB 连线，

选它的理由：① 保持同一色相与同一"品牌同族"推导方式，不新造色相；
② 同时满足两个方向的对比度（作文字、作白字底）；
③ 带余量（4.64 / 6.41），避免不同渲染器取整掉线（规范要求 4.5，取 4.6+）。

`--lg-link` 与它同值（链接即文字）；`--lg-link-hover` 不动（`#9E3054` = 5.06:1，仍更深一档）。

## D35 · 五色标签文字色统一（`GmTag` 对齐 `GmStatusTag`，2026）

### 一、发现

`GmTag` 的五色分支把**五色亮值直接当文字色**（`color: var(--mmh-m5-N)`），

### 二、实测（13% 淡底 / 浅色档；8% / 暗色档）

## D37 · 站点暗色档：一次被探针挡回来的实现（2026）

### 一、缺口

`page-qa` 长期报 **13 条 P3 `dark-missing`**：`site/index.html` 的 6 个模块 +
7 个 `fuyouaicansai/*` 独立产品页，挂上 `data-theme="dark"` 后 400 个采样元素纹丝不动

### 二、做了什么（已回退，方法可复用）

1. 模块 CSS：把散在 12 条规则里的白色叠加字面量抽成填充档 Token（浅色档取值＝原值，
   **浅色观感零变化**），并新增 `[data-theme="dark"]` 档：文字/语义/品牌亮档 + 填充档

`.gm-brand__t strong` 为 `#F3EFEC`。

### 三、为什么回退：门禁模型表达不了它

同一份实现下 `page-qa` 报 **90 条 P1 `contrast-dark`**。逐条追下去，问题在探针而不在实现：

- `page-qa.mjs` 的 `bgOf()` 沿祖先链收集背景层，**只有遇到不透明的 `background-color` 才算
  找到底**；纯 `background-image`（渐变）不置 `broke`。
- 站点与独立产品页的**页面底就是渐变**（`html{background:linear-gradient(...)}`）。
  于是探针在暗色档下找不到底 → 落到 `if (!broke) layers.push([255,255,255,1])` 的**纯白兜底**，
  再把暗色文字压在纯白上算对比度 —— 必然失败。
- 验证性反例：给暗色画布**补上不透明的 `background-color`**（`background-color:#1B1A21`），
  失败数**一条都没少**（90 → 90）；把画布换成纯色同样 90。说明探针的暗色模型在这套层叠结构上
  整体失真，不是"差一点"。

**裁决**：不为了让门禁变绿而改门禁（探针是 CI 里的真实门禁，放宽它等于自毁守门能力），
也不留一个红灯的改进。**先修探针的暗色模型**（至少要能表达"渐变画布"这一层），
再把上面那套实现重新落一遍 —— 步骤与取值已记在本节，可直接复用。

### 四、顺带修掉的两处门禁口径问题（已落地）

1. **`bp` 把规范自己的档报成违规**：`10 · 10.2` 的四档是 `≤767 / 768–1023 / ≥1024 / ≥1366`，
   而 `breakpoint_reg()` 的允许集里**没有 `1023`** → 完全合规的 `@media (max-width:1023px)`
   被报成"非收敛断点"。已修正，并把其余 6 个宽度（900/1200/560/520/480/420）从"泛泛 WARN"
   改成**带理由的登记表**：登记内静默通过，**登记外的新宽度照旧 WARN**。
   负向验证：注入 `733px` 立刻被报出。
2. **`color-html` 的 9 个站点自造暗色值**：`#1B3D33 #1F6B4F #6E7686 #7A5F0D #8ADCC6 #C25064
   #C3C9D3 #F7D27A #FBB4C0` —— 只在站点暗色段出现，且与 `02 · 2.1.9` 的暗色语义值**并不相同**。
   它们是"站点自建暗色档"的证据（同一缺口），先按页面档别名登记并写明待收回。
   负向验证：注入 `#123456` 立刻被报出。

**结果**：`audit.py` 现在**通篇 OK、零 FAIL 零 WARN** —— 这本身就是价值：任何新漂移立刻可见。
