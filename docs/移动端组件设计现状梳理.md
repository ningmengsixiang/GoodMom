## 0. 一页结论

**一句话：移动端设计「规范齐、演示强、代码空、产品另起炉灶」。**

| 层 | 现状概述 | 成熟度 | 关键数字 |
| --- | --- | --- | --- |
| 规范层 | 覆盖广、硬指标明确；但时效停更、口径冲突、登记链断 | **B+**（可用需收口） | 11.1 六类 **59 行 / 58 个组件**；状态 ✅30 / ➕17 / ≋8 / ⏸5；**21 条口径冲突**；**12 项有细则但 00 登记不全** |
| 演示层 | 可触摸的真机样板间，真实交互扎实；但只是内联演示页 | **A−**（参考实现） | **40 个组件**（37 真实 / 3 静态）、**26 类交互**、`mobile-smoke` **86/86**；10 类未演示、13/30 无冒烟断言 |
| 代码层 | 双库 27×2 契约成熟，移动独有件几乎为零 | **D+**（有基础未封装） | 27 个组件中 **13 个含移动适配**；移动独有 28 个里**独立封装 0 个**；`--lg-m-*` Token 在库内 **0 命中** |
| 质量门禁 | 375 / Chromium 全绿，但覆盖窄、有漏检 | **B−**（可信但不可外推） | mobile-smoke 86/86、page-qa P0–P3 全 0、a11y 确证失败 0 / 432 无法判定；**320 档漏检 1 个 P1** |
| 产品层 | 五健 28 屏原型自洽，但与设计系统低一致 | **C−**（线框可信，视觉不可照抄） | **0 Token / 0 `gm-*` 组件 / 0 `lg-icon-*`**；28/28 屏正文 <16px；54 组件族：同名 14 / 近似 20 / **缺失 20** |

**三个核心判断**

1. **「移动端长什么样」已经讲清楚了，但讲法正在分叉。** 10 章给了框架与移动 Token，11 章给了 59 项覆盖地图、18 节细则与 11.6 的 11 个新增件，20.5.5 给了逐条硬指标。问题在维护：10/11 最后实质修订停在 **2026-09-13（V2.9）**，V2.10 只补了库组件与目录封装状态，没回写移动章；21 条冲突（TabBar 圆角 22/24、遮罩 blur 8/16、模糊节点 ≤4/≤6、按钮尺寸两套档……）没有裁决入口。
2. **移动端唯一的完整实现是站点演示，不是组件库。** `preview-mobile.html` 2,729 行内联 HTML/CSS/JS、单 IIFE、无导出；双库 27 个 `Gm*` 里没有一个 NavBar / TabBar / Cell / ActionSheet，`--lg-m-*` 在 `goodmom-ui`、`goodmom-vue`、`frontend-app` 全是 0 命中。演示做得越好，越容易让人误以为「移动组件已经有了」。
3. **新产品已经按自己的方式做了一套。** 儿童五健家长端 28 屏原型 0 外部 CSS、0 Token、0 `gm-*`、0 图标库，正文 11.5–12.5px、热区 24–38px 系统性低于 20.5.5；更根本的是 PRD 主端是**微信小程序**（Taro/uni-app + TDesign/NutUI），而设计系统 **21 份编号规范文档 0 处**提小程序 / Taro / uni-app / TDesign / NutUI。这不是「缺几个组件」，是缺一个端形态。

> 判断口径：本报告把成熟度分为 A（可交付）/ B（可用需收口）/ C（有基础需重做）/ D（缺失）；评分是工程判断，数字才是事实。

### 5.2 门禁外的真实缺陷（1 个）

| 视口 | `document.scrollWidth` | 卡片内容宽 | 第 6 格右沿 | 结论 |
| --- | --- | --- | --- | --- |
| 320 | **337** | 254 | **337** | 整页溢出 17px，触发 shrink-to-fit |

### 5.3 覆盖缺口（按影响排序）

1. **视口单一**：只测 375；320 缺陷完全漏检。
2. **浏览器/设备单一**：仅 Chromium；无 WebKit/Safari、iOS Safari、Android 真机；`dvh`、`backdrop-filter`、`scroll-snap`、`safe-area`、触摸/滚动竞态未验证（而这正是本模块大量使用的特性）。

5. **暗色无渲染级 a11y**：只有 page-qa 一套探针。

7. **无辅助技术/缩放**：无 VoiceOver/TalkBack、无 200% 字号。
8. **无视觉回归基线**：没有移动端截图 diff。
9. **范围窄**：只测演示模块，双库封装、6 个产品页、28 屏原型都不在门禁内。

## 9. 结论与优先级建议

### 9.1 总体判断

1. **移动端设计系统是「两层半」的**：规范层和演示层已经能支撑设计评审与方案定稿；代码层只能提供壳与通用件；产品层另起炉灶。三者之间没有「组件契约」这一层做桥。
2. **当前最大风险不是缺组件，而是缺收口**：21 条冲突、12 项登记不全、10/11 停更 36 天。继续在旧口径上做新页面，会把冲突带进实现。
3. **新产品的端形态（微信小程序）设计系统尚未回答**。这不是补 10 个组件能解决的，需要一次「端形态决策」。

### 9.2 P0（建议 2 周内）：先止血，再抽骨架

| # | 动作 | 验收 |
| --- | --- | --- |
| P0-1 | **裁决 8 条冲突**（6.1），回写 10/11/20/03/06；冻结移动规范基线到 V2.11 | 8 条全部有唯一值；20.12 更新；`audit.py` 相关项不变红 |
| P0-2 | **补登 12 项**到 00（11 项新增行 + Dropdown 修正既有行），修正 Dropdown 移动 ⏸ 矛盾；给 `--lg-m-*` 18 个 Token 在两库落地 | 00 行数 99→110；两库 `--lg-m-*` 命中 >0；`coverage.py` 口径扩展 |
| P0-3 | **抽取 5 个 P0 组件**：NavBar、TabBar、ActionSheet + BottomSheet、Cell、SearchBar（React/Vue 同契约 + story + 44 热区断言） | 双库各 5 个组件；`check-component-contract` 通过；story 可在 375 视口打开 |
| P0-4 | **门禁补面**：mobile-smoke 支持视口参数并加入 320 档 + 记录页 + 弹层打开态；layout-gate 移动模块白名单收窄 | 320 OTP 缺陷被门禁捕获；320/375/414 全绿 |
| P0-5 | **修 320 OTP 溢出（P1）** 与 **D1 React GmClientCard ≤767 分叉** | 320 `scrollWidth=320`；两库 `@media` 选择器集合一致 |

### 9.3 P1（1–2 月）：移动交互闭环

- 列表/表单：PullRefresh、LoadMore、SwipeAction、Picker（滚轮）、Calendar、Stepper、OTP、NumberKeyboard。
- 反馈/辅助：NoticeBar、ImageViewer、ErrorBlock、SafeArea、Sticky、WaterMark、Footer、CapsuleTabs、Selector。
- 工程：Storybook 加 `addon-viewport` 与移动 stories；`check-style-parity` 把 `@media` 纳入比对；双库各补 10 个移动组件的 play 断言。
- 演示层：补齐 Dialog、Result、表单校验、Upload 拍照/相册 Sheet、OTP 倒计时、Rate 半星、Steps 竖版、Footer 玻璃条；13 项无断言补上 smoke。

### 9.4 P2（产品化）：领域件与端形态

- 领域件：孕周卡、产检卡、胎动/体重/宫高、分娩准备、宝宝头像卡、疫苗卡、儿保卡、喂养记录。
- **五健前置决策**：① 五健维度语义层（色/图标/风险分级/状态词）先立项，登记 00/02/09/15；② 小程序端形态决策（TDesign/NutUI 映射 vs 自建 Web 移动组件）；③ 移动雷达是否解禁（00 #74 vs 首页需求）；④ 28 屏原型按 20.5.5 重绘一版，作为落地基线。

### 9.5 面向五健的落地路线（建议顺序）
